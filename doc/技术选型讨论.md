  结论先说清楚：如果你的目标只是“把已有视频变成可选 RTP/RTSP + H264/H265/MJPEG
  的测试流源”，现成工具足够；如果你的目标是“系统性做协议互操作和边界行为测试，包括行业惯例、异常时序、非标准但常见实现差异”，最终需要一个可编程发送端，现成方案只能覆盖一部分。

  现成可用
  FFmpeg、GStreamer、gst-rtsp-server、MediaMTX、VLC 这类可以很快搭出虚拟流源。

  - FFmpeg
  适合 MP4 -> RTP/RTSP 的快速推流和基础互通验证。能做 H264/H265/MJPEG 的常规发送，但对 RTP 包级行为、RTSP 会话细节、异常包构造不够细。
  - GStreamer + gst-rtsp-server
  这是现成方案里最接近你目标的。appsrc 可以由程序主动喂帧或喂编码后的 GstBuffer，gst-rtsp-server 对外提供 RTSP server。适合做“可控虚拟摄像头/测试流源”，并能比较细地控制节奏、码流、封装方式。
  - MediaMTX
  更像媒体服务器/代理/中转，适合快速验证 RTSP/RTP 互通、转发、录制回放，不太适合做畸形包、边界 RTP 行为、异常 RTSP 会话。
  - VLC
  可用于简单回放和推流验证，但自动化、参数控制和协议测试深度都一般。

  需要自研或半自研
  如果要覆盖更深的协议测试，建议走“库 + 自定义发送逻辑”。

  - gortsplib（Go）
  很适合做自定义 RTSP server/client 和测试源。官方能力覆盖 RTSP server/client、RTP/SDP 处理，并明确支持 H264/H265/MJPEG 相关编解包。适合做自动化测试平台。
  - Live555（C++）
  更底层，更适合精细控制 RTSP 会话、RTP 发送、时序和兼容性行为，但开发成本更高。
  - 纯自定义 RTP sender
  如果你要精确控制 sequence、timestamp、marker bit、SSRC、packetization-mode、SPS/PPS/VPS 注入策略、FU-A/STAP-A、乱序/丢包/重复包/错误长度等，这通常要自己发包，或者在 gortsplib / GStreamer appsrc + payloader 之外再下沉一层自己控制 RTP。

  输入源差异
  输入格式决定你能控制到什么程度。

  - MP4
  最容易变成稳定测试流源，但保真度最低。它保留的是媒体内容和封装，不保留原始 RTP 包边界、原始 RTSP 会话、时间戳细节、异常包形态。所以适合“功能互通”和“标准路径”测试，不适合复现现场协议问题。
  - RTP capture / PCAP
  这是做高保真协议回放最有价值的输入，因为保留了原始 RTP 包、时间戳、序号、分片/聚合形态。适合复现兼容性 bug，也适合作为“基线流”再做变异测试。
  - RTSP/RTP/TCP 抓包
  适合复现完整 RTSP 建链、SETUP/PLAY、interleaved RTP over TCP 这类问题。但如果只是 L2/L3/L4 的 pcap 重放，例如 tcpreplay 那一路，通常不能直接替代“虚拟流源”，因为端口、会话状态、RTSP
  控制面、客户端协商、NAT/地址、时钟关系都可能失真。它更像网络层回放，不是应用层可控流源。

  对协议参数和异常行为的支持
  这里是关键分水岭。

  - FFmpeg / MediaMTX / VLC
  适合常规发送，不适合深度异常构造。
  - GStreamer
  能做到中等到较高可控，特别是自己控制 appsrc、payloader、caps、发送节奏时；但若要发故意违规或非常规 RTP，仍可能需要自定义元素或旁路发送。
  - gortsplib / Live555 / 自定义 sender`
  最适合做协议测试矩阵，可以直接控制 RTSP 响应、RTP packetization、时序和边界条件。

  以 H264/H265 为例，真正会踩兼容性坑的点通常包括：

  - packetization-mode
  - SPS/PPS 或 VPS/SPS/PPS 是带内发、带外发、重复发还是延迟发
  - FU-A / STAP-A / H265 fragmentation/aggregation 的使用方式
  - marker bit
  - timestamp / sequence 连续性
  - RTP over UDP vs RTP over RTSP(TCP interleaved)
  - RTSP DESCRIBE/SETUP/PLAY 的 SDP 与 transport 协商细节

  这些并不是单靠“能把 MP4 推成 RTSP”就能覆盖。

  推荐路线
  如果你要尽快做出可用系统，我建议分两层：

  1. 第一层，现成可用源
  用 GStreamer + gst-rtsp-server 做主测试源，输入支持 MP4、程序生成帧、基础转码，输出支持 RTSP，必要时再补裸 RTP 发送。
  2. 第二层，协议测试核心
  用 gortsplib 或自定义 RTP sender 做可编程变异层，专门覆盖 RTP/RTSP 参数组合、异常包、行业惯例和非标准边界行为。
  3. 第三层，保真回放
  对 PCAP/RTP capture 做“解析后重发”，不要直接依赖 tcpreplay 这类 L2/L3 重放工具充当应用层测试源。

⏺ 基于你刚定死的 4 个范围，这个项目的核心不应该是“媒体推流工具”，而应该是“可编程的 RTP/RTSP 回放与变异引擎”。结论上，我建议选 Go 做主实现，gortsplib 负责 RTSP 控制面，pion/rtp 或自定义 RTP 包构造负责 RTP/UDP
  发送，gopacket 负责 PCAP 解析；FFmpeg 作为 MP4 导入和必要转码的辅助工具，而不是系统核心。

  原因很直接：你现在把 RTSP + RTP/UDP、H264/H265/MJPEG、异常/变异流、MP4 + PCAP/RTP capture 都列成必选后，真正困难的部分已经不是“把视频发出去”，而是这些能力：
  - 保留或改写 sequence、timestamp、marker bit、SSRC
  - 控制 H264/H265 的分片/聚合方式，SPS/PPS/VPS 注入策略
  - 控制 MJPEG 的 RTP 打包细节
  - 支持 RTSP 协商层面的正常/异常行为
  - 从 PCAP 高保真提取后再定制化重放

  这几件事如果把 GStreamer 或 gst-rtsp-server 放在系统中心，后面会很快碰到上限。所以我的选型建议是：

  推荐架构
  1. Control Plane
  用 Go 实现任务编排、配置、测试场景管理、回放控制、变异规则管理。
  2. Input Ingest
  MP4 路径不要直接拿播放器式思路处理，建议做“导入归一化”：
  - 用 FFmpeg 把输入标准化为可重放资产
  - H264/H265 转成 Annex B elementary stream
  - MJPEG 转成 JPEG frame sequence + timing manifest
  - 同时生成一份统一元数据，记录 fps、duration、codec params、关键帧信息

  PCAP/RTP capture 路径则做“高保真抽取”：
  - 用 gopacket 解析 RTP/UDP
  - 支持提取 RTSP interleaved TCP
  - 保留原始包边界、序号、时间戳、marker、payload 分片形式
  - 生成可 replay 的 session bundle

  3. Canonical Session Model
  这是整个系统最关键的一层。无论输入来自 MP4 还是 PCAP，都先转成统一内部模型，例如：
  - SDP/codec config
  - stream metadata
  - packet timeline
  - frame/NALU references
  - RTSP session script（如果输入里有控制面）

  只要这层建对了，后面的 RTSP、RTP/UDP、异常变异、录制复现都能共用。

  4. Protocol Engine
  拆成两部分，不要绑死在一个库里。
  - RTSP engine：优先用 gortsplib 承担 DESCRIBE/SETUP/PLAY/TEARDOWN、SDP、Transport 协商
  - RTP engine：自己掌控发包节奏、包内容和错误注入；正常流可以走标准 packetizer，异常流走自定义 sender

  这个拆法很重要，因为后面你一定会遇到“RTSP 正常但 RTP 故意违规”的场景。

  5. Mutation Engine
  单独做成规则层，不要散在各个 sender 里。至少分三类：
  - Session-level：异常 SDP、Transport header、响应码、Header 顺序/缺失/重复
  - Packet-level：乱序、丢包、重复包、错误长度、错误 marker、错误 payload type、SSRC 切换
  - Codec-level：SPS/PPS/VPS 缺失、延迟、重复、带内/带外切换，FU-A/STAP-A 或 HEVC fragmentation 变体，MJPEG RTP 头字段异常

  技术栈建议
  - 主语言：Go
  - RTSP：gortsplib
  - RTP 包模型：pion/rtp
  - 抓包解析：gopacket
  - MP4 导入/转码：FFmpeg CLI
  - 配置格式：YAML 或 JSON
  - 测试描述：建议做成 declarative profile，而不是把场景写死在代码里

  为什么不建议把 GStreamer 放核心
  GStreamer 适合做标准媒体 pipeline，但你的硬需求里“异常/变异流”是必须项，这会让系统重心落在包级行为和协议行为上，而不是媒体处理。GStreamer 可以作为后续辅助模块保留，比如：
  - 校验标准路径输出是否可播
  - 生成某些测试输入
  - 做对照组 sender

  但不建议让它主导整个架构。

  v1 的合理切分
  第一阶段先把“架构跑通”，不要一上来把所有变异点铺满：
  1. 先支持 RTSP 和 RTP/UDP 两种输出链路
  2. 编码先全上 H264/H265/MJPEG，但异常点优先做 H264
  3. 输入先同时打通 MP4 import 和 PCAP replay
  4. 变异能力第一批只做高价值项： 
    - seq/timestamp/marker 异常
    - 丢包/乱序/重复
    - H264 SPS/PPS 注入策略
    - RTSP Transport/SDP 常见兼容性差异

  这样做能最快产出一个“既能正常发，也能有针对性造问题流”的版本。
